## 一、项目最终目标

NovelSim 的产品目标已经明确为：

> **将长篇网络小说自动编译成持久化多智能体世界，让用户从任意已发布章节进入、改变剧情，并持续生成属于该用户的个人小说世界线。**

完整产品闭环：

```text
小说正文
→ 编译章节、角色、场景、事实、关系和章节起始状态
→ 用户从任意已发布章节进入
→ 玩家干预或世界自动演化
→ NPC 根据记忆、信息边界、关系和目标行动
→ 世界引擎提交权威事件并修改状态
→ 将已提交事件持续写成对应小说正文
→ 用户阅读个人世界线小说
→ 继续干预、结算并进入下一章
```

### 1.1 两个必须分离的领域

#### 世界模拟层

负责：

- 行动者是谁；
- 行动动机；
- 信息来源与角色认知边界；
- 行动结果；
- 状态、事实、关系、物品、记忆和剧情线变化；
- 权威事件提交与回放。

#### 小说稿件层

负责把已经发生的权威事件写成连续文学正文，包括：

- 场景；
- 动作；
- 对白；
- 情绪与反应；
- 叙事节奏；
- 与上一段稿件的衔接；
- 玩家干预造成的分支；
- 不违背权威世界状态的文学表达。

核心原则：

> **世界状态是事实，世界事件是骨架，生成小说是文学表达。**

稿件生成失败不能回滚已经提交的权威世界事件；小说正文属于可重试、可追加 revision 的派生产物。

## 二、当前已经确定的产品与章节模型

当前使用原始小说《第一狂妃：废柴三小姐》。

已经确定：

- 整本小说正文在目录导入阶段预先缓存。
- 一个章节是一个独立进入点。
- 用户可以直接选择任意**已发布**章节进入，不需要完成前置章节。
- 直接进入第 N 章创建独立 root session。
- 结算后进入下一章使用 transition 协议创建 child session，并只继承白名单字段。
- 直接进入和跨章继承即使进入同一个章节，也不能合并成同一条世界线。
- passage 是一次稿件生成批次，不是文学章节。
- 文学章节归属由 passage 预留时固化的 `entry_id + entry_revision + chapter_number` 决定。
- `manuscript_sequence` 是整条 campaign 的稿件阅读顺序。

重要区别：

```text
正文缓存 ≠ 世界状态初始化 ≠ 章节入口发布
```

截至 2026-08-28 最后一次经授权核对，已知默认数据状态为：

```text

章节目录入口：4228
已发布章节入口：2（第 1 章、第 6 章）
其余章节：只有正文缓存，尚未全部具备 chapter-start snapshot/runtime package
```

**注意：最后一轮稿件修复严格禁止访问默认数据库，因此本文没有重新核对上述默认数据数量。新窗口不得把旧统计当作刚刚读取的实时数据。**

## 四、最新完成：个人世界线稿件系统修复

最后一轮核心任务是修复“我的小说”中出现的事件日志式正文、重复章节头、内部 ID 泄漏和重复对白问题。

修复前的实际问题包括：

- 每个 passage 都重复显示 `CHAPTER 01 / 第 1 章`；
- passage 被错误表现成章节；
- 正文出现 `ability:mystic.pull_into_space` 等能力 ID；
- 正文出现 `canonical.entered_mystic_space` 等内部 flag；
- 正文与 dialogue 卡片重复；
- dialogue 卡片显示 `char_jiyue` 等角色 ID；
- 大量机械的“承接前事”“随后”；
- deterministic writer 像 operation 日志，不像小说；
- 中文两端对齐造成异常字距；
- 历史 ready passage 无法安全追加重写 revision。

这些问题已经完成系统性修复。

### 4.1 统一玩家可见正文契约

当前契约：

- `paragraphs` 是完整且唯一的玩家可见正文；
- `text == "\n\n".join(paragraphs)`；
- 对白必须已经按叙事顺序写入 `paragraphs`；
- `dialogues` 只保存结构化证据，不在普通阅读器中再次渲染；
- `system_hints` 是附加系统提示，不是第二份正文；
- `story_beats` 不是正式小说正文。

### 4.2 Deterministic writer 已重构

`engine/manuscript_writer.py` 中的 deterministic writer 现在：

- 优先读取可信的 presentation narration/dialogue；
- 不再忽略 narration；
- 不再机械添加“承接前事”和每事件固定“随后”；
- 按事件、动作和对白自然分段；
- 不输出 operation 的 raw `path`、`reason`、dict/list；
- `set_flag`、`increment_value`、`update_relation`、`set_relation`、`update_belief`、`change_identity`、plot 操作、`update_psyche`、`advance_plan`、`record_evidence`、`add_fact`、`record_propagation`、`form_alliance` 等内部操作不会被逐条日志化；
- 未知角色、地点和物品使用安全中文泛称，不回退内部 ID；
- 内部变化继续保存在 fact claims、source operations 和审计链中。

### 4.3 内部标识质量门禁

普通玩家可见正文禁止出现：

```text
char_*
character_*
item_*
loc_*
location_*
fact_*
event_*
ability:*
capability:*
canonical.*
operation path / operation 名称
```

门禁采用精确模式，不是简单删除所有英文，因此以下普通文学英文仍允许：

```text
Alice checked her ability to remain calm before the ceremony.
```

新增检查还包括：

- `paragraphs` 与 `text` 必须严格表示同一正文；
- 相邻长段落完全重复或高度相似时拒绝；
- 短句文学重复不会误杀；
- source event 顺序、连续性和世界版本范围必须正确；
- fact claim 必须能映射到来源 operation；
- writer 不能篡改 passage 身份、章节身份或来源事件。

### 4.4 LLM manuscript writer 已接入 Web 编排

新增统一的 `MANUSCRIPT_WRITER_FACTORY`。

Web writer 模式：

```text
NOVELSIM_MANUSCRIPT_WRITER=reuse_narrative
NOVELSIM_MANUSCRIPT_WRITER=deterministic
NOVELSIM_MANUSCRIPT_WRITER=llm
```

默认值：

```text
reuse_narrative
```

重要安全行为：

- 不会因为机器上存在 API key 就自动调用真实模型；
- 只有显式设置 `NOVELSIM_MANUSCRIPT_WRITER=llm` 才构造 LLM 稿件 writer；
- 普通回合、联合规划、自动演化和稿件 retry 统一进入 `_persist_manuscript_batch()`；
- 测试可以 monkeypatch factory 注入 fake writer；
- LLM/provider/schema/runtime 失败时，新事件稿件安全降级为 deterministic；
- 稿件失败或降级不回滚权威事件；
- metadata 只记录有限的 fallback 类型，不保存 provider 原始响应。

LLM 只能返回表现层字段：

```text
title
paragraphs
text
referenced_entity_ids
dialogues
system_hints
viewpoint
continuity_summary
```

以下字段由服务器生成，模型不能决定：

```text
passage_id
manuscript_id
source_event_ids
source_fingerprint
from_world_version
to_world_version
fact_claims
writer_version
input_hash
generation_kind
revision
```

上一 passage 的完整正文会以 `previous_passage_text` 进入下一次写作上下文。

### 4.5 历史 ready passage 支持安全追加 revision

稿件重写请求新增：

```json
{
  "session_id": "...",
  "rewrite_ready": true,
  "expected_revision": 3
}
```

行为：

- 只有显式 `rewrite_ready=true` 才能重写健康 ready passage；
- 必须提交 `expected_revision`；
- SQLite 使用 `BEGIN IMMEDIATE`；
- PostgreSQL 使用 `SELECT ... FOR UPDATE`；
- expected revision 不匹配时抛 `ManuscriptRevisionConflict`；
- Web 返回 HTTP 409；
- stale 请求不追加 revision；
- stale 请求不覆盖正文；
- stale 请求不增加 manuscript revision；
- stale 请求不写 passage `last_error`；
- 成功后追加不可变 revision，并设置 parent revision ID；
- passage ID、session、entry、chapter、sequence、source fingerprint 和世界版本范围固定不变；
- 重写不调用 `commit_turn`；
- 不提交或重放世界事件；
- 不修改 `WorldState`、turns 或已有 event JSON。

### 4.6 历史稿件一致性边界

已实现：

```python
get_state_at_version(session_id, world_version)
```

新会话和 v3 导入会保留不变基线快照，指定版本通过基线加 append-only events 重放。历史 passage 重写使用其 `to_world_version` 对应状态，因此可执行完整的 speaker alive、knowledge leak、item owner、relation 和 belief 校验，不会用最新状态否定旧事件。

迁移前已存在的会话没有可验证的原始基线，迁移时以当前快照作为最早可用版本。对更旧 passage 仍保留 `validate_current_state=False` 的安全降级，不伪造或猜测历史状态。

### 4.7 Campaign 跨 session 连续稿件

存储协议保留：

```python
list_manuscript_passages(session_id)
```

它仍只返回当前 session passage，避免破坏 session 导出、恢复和 retry 的原语义。

新增：

```python
list_campaign_manuscript_passages(session_id)
```

用于：

- writer 获取整条 campaign 真正的上一 passage；
- player-view 按 `manuscript_sequence` 返回父子 session 的连续个人小说；
- 子 session 阅读父章节稿件；
- 不把 campaign 查询强行替换所有 session-only 查询。
